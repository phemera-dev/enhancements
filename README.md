# Phemera enhancements

This repository holds Phemera Enhancement Proposals (PEPs). A PEP is a design document that describes a significant change to Phemera, the reasoning behind it, and how it will be built and rolled out. The process is modeled on Kubernetes KEPs and Python PEPs, scaled down for a young project.

PEPs exist so that design decisions happen in the open and leave a record. Code review shows how something was built. A PEP shows why it was built that way, which alternatives were rejected, and what security tradeoffs were accepted. For a privileged access management system, that record matters to contributors and to the people who have to trust the software.

The full process is defined in [PEP-0001](peps/0001-pep-process/README.md). This page is a summary.

## When is a PEP needed?

Write a PEP for changes that other contributors or operators need to agree on before the code lands. Typical cases:

- A new user-facing feature or a new component.
- A change to the security model: authentication, authorization, credential handling, session brokering, audit logging, or trust boundaries between components.
- A breaking change to an API, CLI, configuration format, or on-disk or wire format.
- A new external dependency that becomes part of the trusted computing base.
- A change to project governance or to this process.

Bug fixes, refactors, documentation, and small improvements that do not change behavior go straight to a pull request in the relevant code repository. When in doubt, open a GitHub issue in this repository and ask.

## How to submit a PEP

1. Open an issue using the "PEP tracking issue" template. Describe the problem in a few paragraphs and gather early feedback before writing a full design.
2. Copy `peps/0000-template/` to `peps/NNNN-short-title/`. Take the next free number (see the index below) and use lowercase, hyphenated words for the title.
3. Fill in the front matter and as many sections as you can. Set `status: draft`.
4. Open a pull request. Discussion happens on the PR. Small, early PRs are fine; a PEP does not need to be complete to be merged as `provisional`.
5. Once approvers agree on the direction, the PEP is merged as `provisional`. When the design details are settled, a follow-up PR moves it to `implementable` and implementation can start.
6. When the work ships, update the status to `implemented`.

Run `scripts/validate-peps.py` locally before pushing. CI runs the same checks.

## PEP statuses

| Status | Meaning |
|---|---|
| `draft` | Under discussion in a pull request. Not merged yet. |
| `provisional` | The project agrees the problem is worth solving and the direction is sound. Design details may still be open. |
| `implementable` | The design is approved. Implementation can begin. |
| `implemented` | The change has shipped in a release. |
| `deferred` | Accepted in principle, but nobody is working on it. |
| `rejected` | Approvers decided against it. The PEP records why. |
| `withdrawn` | The author dropped it. |
| `replaced` | Superseded by another PEP, named in `superseded-by`. |
